# Login and membership quotas

[built]

**Contract**
- Login is **Better Auth email+password**, not Google OAuth — see
  [ADR 0008](../decisions/0008-better-auth-email-password.md) for why the
  originally-planned Google flow was dropped.
- The website Worker (`website/worker/`) is the only thing holding
  secrets or touching the database; the desktop app is a bearer-token
  client, same public-client posture the original Google plan assumed.
- Membership tiers and quota math are owned by
  [business/pricing.md](../business/pricing.md); this doc owns the
  *mechanism* (how a request gets authenticated and how a quota is
  checked), not the tier numbers.

## Flow

1. Desktop app's `#view-login` (`sidebar.js`, `sidebar.html`) is a native
   email/password form — no browser round trip, no loopback listener.
   It calls the Worker's Better Auth routes directly
   (`/api/auth/sign-up/email`, `/api/auth/sign-in/email`).
2. Better Auth (`website/worker/better-auth.ts`) returns the session
   token in the `set-auth-token` response header (the `bearer()` plugin,
   not cookies — the desktop webview has no cookie jar shared with the
   Worker's origin).
3. Desktop stores the token via `store_session_token` /
   `get_session_token` / `clear_session_token`
   (`spikes/tauri-overlay/src-tauri/src/lib.rs`), backed by the
   [`keyring`](https://docs.rs/keyring) crate — OS credential store, not
   a plaintext file. On startup, a stored token is checked against
   `/api/me`; a 401 clears it and falls back to the login view.
4. Every authenticated request sends `Authorization: Bearer <token>`.
   The Worker validates it via `auth.api.getSession()`
   (`membershipFromBearer` in `worker/auth.ts`), then joins to the
   product's own `memberships` table.

## Database

Better Auth owns `user` / `session` / `account` / `verification`
(`worker/db/auth-schema.ts`, generated by `@better-auth/cli generate`
against the stub `auth` export in `better-auth.ts` — regenerate rather
than hand-edit if the Better Auth config changes). The product owns
`memberships` and `skill_runs` (`worker/db/schema.ts`,
`migrations/0002_create_auth_and_quotas.sql`), kept separate because
plan/quota logic isn't an auth concern.

A new account defaults to `plan=free`, `status=active`
(`better-auth.ts`'s `databaseHooks.user.create.after`), unless its email
is on the `OWNER_EMAILS` allowlist (comma-separated `wrangler.jsonc`
var), in which case it starts `owner` — the way a teammate gets
unlimited access without manual D1 surgery.

## Endpoints

- `GET /api/me` — `{ email, plan, status, skills_remaining,
  skills_included, can_save_skills }` or 401. `skills_remaining` is
  `null` for `owner` (unlimited).
- `POST /api/skills/start` — call when a new goal starts
  (`sidebar.js`, after Research succeeds — not before, so a request the
  user never actually commits to doesn't burn quota). Inserts a
  `skill_runs` row or 403s with the same quota fields when the plan's
  allowance is used up. Accepts an optional `{ cost }` (clamped 1–1000)
  for a future variable-cost skill; every caller today passes the
  default of 1.

Quota counting (`countSkillRuns` in `worker/auth.ts`): `free` sums
lifetime; `starter`/`plus` sum since the start of the current calendar
month; `owner` is never counted.

## Deferred

- **Email verification** — `requireEmailVerification: false` today; see
  [BACKLOG.md](../BACKLOG.md) BL-015. Needs an email-sending provider
  before this can flip on.
- **Stripe billing** — `starter`/`plus` are hard-capped and hand-set in
  D1; no metered overage billing yet (`pricing.md`'s Starter overage
  rate is specified but not wired to a payment processor).
- **Session expiry UX** — what the desktop app shows mid-session if a
  token is revoked isn't designed beyond falling back to the login view
  on the next 401.
